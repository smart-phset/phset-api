## Development PostgreSQL recovery and credential revocation

The original container was absent. The existing `api_postgres-data` volume had
the expected `api` Compose project/volume labels and a PostgreSQL 18 cluster with
an unclean shutdown. A protected full copy was verified by per-file SHA-256,
then an isolated network-disabled copy was recovered first. Before starting the
original data, that copy confirmed the `smartphset` database/role, V1–V4 successful
Flyway history, 4,142 AI scans and 4,212 detection boxes.

The original volume was then started as `smartphset-postgres`, using its existing
cluster directly with `postgres -D /var/lib/postgresql/18/docker`. Initialization
was bypassed. Only stale startup metadata was moved aside; no database, table,
container or volume was deleted/reset. The recovered development server publishes
only `127.0.0.1:5432`, uses the existing `api_smartphset-network` and restarts
unless stopped. TCP authentication now requires SCRAM; Unix socket admin access
remains local to the container.

The affected actual role password was rotated to a generated credential, not
merely changed in POSTGRES_PASSWORD. Both POSTGRES_PASSWORD and DB_PASSWORD in
the ignored private `.env` were updated atomically; mode remains 0600. Verification
proved new-password TCP login succeeds and old-password TCP login fails.
All database names and every public table's row count/content fingerprint were
preserved. No password, verifier or private configuration is included in this report.
Reload the private environment in existing development shells before starting clients.

Private recovery backups are under the Git-ignored, root-only
`.release-private/postgres-recovery-lo7dtnrq/`. They contain sensitive offline
recovery material; do not upload, force-add or use them as active credentials.
The isolated identity container is stopped and retained; the recovered original
volume is running. To restart that existing development service later:

```bash
docker start smartphset-postgres
```

The recovery container deliberately bypasses image initialization and is not a
Compose-managed recreation. Inspect its existing mounts/configuration before
changing its lifecycle; do not initialize a replacement database or remove its
volume. Existing dev/test PostgreSQL containers were left unchanged.

Known local private configurations and other existing PostgreSQL container
configuration were checked for exact credential reuse. Only the API's two local
DB settings matched. Read-only SSH comparison verified that the running AWS API's
database credential and its private env-file credential match each other, point
at Neon, and differ from the exposed development credential. No production
password or database was modified. These findings cover the known environments
inspected, rather than every possible external copy of a credential.

## Reproducing the release build

The published tag already exists; do not overwrite it. For a future version,
use a new unique tag. The completed v1.1.0 build used the existing multistage
Java 25 Dockerfile, the full Gradle suite and an archive of the committed source:

```bash
./gradlew --no-daemon test build --rerun-tasks
# Export the selected reviewed commit into a fresh empty build directory:
git archive 9f9f3b52bbc593de5150119497c0dd91a3578d4c | tar -x -C /path/to/empty/build-directory
# Historical completed build command; choose a NEW tag for another build:
docker build --no-cache --platform linux/amd64 \
  --label org.opencontainers.image.revision=9f9f3b52bbc593de5150119497c0dd91a3578d4c \
  --label org.opencontainers.image.version=1.1.0 \
  --label org.opencontainers.image.source=https://github.com/smart-phset/phset-api \
  -t ratanaksaren/smartphset-api:1.1.0 /path/to/empty/build-directory
bash scripts/release/smoke-image.sh ratanaksaren/smartphset-api:1.1.0
```

No test connected to production MQTT or Neon. Source/runtime secrets were not
passed as image build arguments. Build/test logs and detailed audit evidence
were retained locally; private recovery material is excluded from Git.
